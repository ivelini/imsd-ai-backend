# Функциональные требования — Пользовательская часть

> **Основание:** ТЗ пользовательской части (`documentations/tz/user-functional-spec.md`)
> **Версия API:** `/api` — публичные + клиентские эндпоинты (Sanctum для авторизованных)

---

## 1. Города и доставка

### 1.1. Выбор города

**FR-1.1.1** При первом заходе пользователь должен выбрать свой город из списка доступных городов.

**FR-1.1.2** Выбранный город сохраняется: в сессию (для гостя) и в профиль (для авторизованного). При следующих визитах город определяется автоматически по сохранённым данным.

**FR-1.1.3** Пользователь должен иметь возможность переключить город в любой момент через специальный виджет без перехода на отдельную страницу. При смене города цены, доступные точки выдачи и сроки доставки пересчитываются для нового города.

**FR-1.1.4** Товар считается доступным в городе, если в городе есть хотя бы одна точка выдачи И товар есть в наличии у поставщиков.

**FR-1.1.5** Если товара нет в наличии, система должна показать примерный срок появления.

**FR-1.1.6** Система должна предоставлять список доступных городов для выбора.

### 1.2. Точки выдачи

**FR-1.2.1** Система должна предоставлять список точек выдачи в выбранном городе (адрес, режим работы, контакты).

**FR-1.2.2** Пользователь должен иметь возможность посмотреть точки выдачи на карте (опционально — через iframe карты).

**FR-1.2.3** В карточке товара система должна показывать, доступен ли товар для самовывоза в выбранном городе.

### 1.3. Доставка

**FR-1.3.1** Пользователь может выбрать способ получения: самовывоз из точки выдачи или курьерская доставка.

**FR-1.3.2** Если в городе нет точек выдачи, доступна только курьерская доставка.

**FR-1.3.3** На карточке товара система должна показывать **конкретный** срок доставки в выбранный город в рабочих днях, рассчитанный на текущий момент (с учётом дня недели и времени посещения).

**FR-1.3.4** В корзине срок доставки должен пересчитываться на момент создания заказа.

### 1.4. Сроки доставки (расчёт)

Расчёт срока доставки — внутренняя логика, невидимая пользователю. FR для реализации.

**FR-1.4.1** Система должна рассчитывать срок доставки по формуле:
```
срок = время_от_склада_до_нас + время_из_Челябинска_до_города_клиента
```

**FR-1.4.2** Время от склада до нас зависит от расписания отгрузки склада:
- если заказ сделан до времени отсечки в день отгрузки → `days_before`
- если после отсечки или не в день отгрузки → `days_after`

**FR-1.4.3** Система должна показывать клиенту конкретный срок на текущий момент (с учётом дня недели и времени). Если клиент не успевает к отсечке — срок считается до следующей отгрузки.

**FR-1.4.4** Система должна предоставлять справочник времени доставки из Челябинска до городов (настраивается в админке).

## 2. Каталог и поиск

### 2.1. Поиск по автомобилю

**FR-2.1.1** Система должна предоставлять автокомплит для поиска автомобиля: марка → модель → год выпуска → модификация (двигатель + комплектация).

**FR-2.1.2** После выбора модификации система должна показать список совместимых типоразмеров, разделённый на три группы: **родные (OEM)**, **допустимые замены** и **тюнинг**.

**FR-2.1.3** Для каждого типоразмера система должна показать количество доступных товаров (шин и/или дисков) в каталоге.

**FR-2.1.4** Из результатов подбора пользователь должен иметь возможность:
- перейти в каталог с предустановленными фильтрами по выбранному типоразмеру
- сохранить автомобиль в «Гараж»

**FR-2.1.5** При переходе в каталог после подбора по автомобилю контекст авто должен сохраняться: на странице каталога отображается, для какой машины ведётся подбор, и пользователь может переключаться между типоразмерами (родной / замена / тюнинг) без повторного ввода автомобиля.

### 2.2. Фасетный каталог

**FR-2.2.1** Каталог должен поддерживать два типа товаров: шины (`tire`) и диски (`wheel`). Каждый тип имеет свой набор фильтров.

**FR-2.2.2** Набор фильтров для шин:
- ширина профиля
- высота профиля
- посадочный диаметр
- сезон (зима/лето/всесезон)
- шипы (да/нет)
- индекс скорости
- индекс нагрузки
- бренд
- run-flat (да/нет)
- усиленная/XL (да/нет)
- год выпуска
- только в наличии
- цена (от, до)

**FR-2.2.3** Набор фильтров для дисков:
- сверловка (PCD)
- вылет (ET)
- ступичное отверстие (DIA)
- ширина
- диаметр
- материал (литые/штампованные/кованые)
- цвет
- бренд
- только в наличии
- цена (от, до)

**FR-2.2.4** Для каждого значения фильтра система должна показывать количество подходящих товаров (count). При выборе одного фильтра остальные пересчитываются.

**FR-2.2.5** Если значений в фильтре больше N (например, бренды), должен быть доступен поиск внутри фильтра.

**FR-2.2.6** Состояние всех активных фильтров должно кодироваться в URL (глубокая ссылка), чтобы ссылкой можно было поделиться.

**FR-2.2.7** Сортировка: по цене, бренду, диаметру, дате добавления — по возрастанию или убыванию.

**FR-2.2.8** Пагинация: по умолчанию 48 товаров на странице. Страницы листаются.

**FR-2.2.9** Ответ каталога должен включать:
- список товаров (с базовой информацией: название, цена, фото, бренд, основные характеристики)
- фасеты (для каждого фильтра — значения и количество)
- метаданные пагинации

### 2.3. Карточка товара

**FR-2.3.1** Система должна отображать полную информацию о товаре:
- все характеристики (зависит от типа: шина или диск)
- галерея изображений (основное + дополнительные фото)
- для шин: маркировка боковины с пояснениями (дата производства, индексы, обозначения)
- текущая цена (с учётом скидок по акциям)
- остатки по складам выбранного региона
- сроки доставки

**FR-2.3.2** На карточке товара должны быть блоки:
- **Совместимые автомобили** — на какие машины подходит этот товар
- **Аналоги** — товары того же типоразмера, других брендов
- **Сопутствующие товары** — шины к дискам, диски к шинам, крепёж

### 2.4. Сравнение

**FR-2.4.1** Пользователь должен иметь возможность добавлять товары в сравнение (до 4 одновременно).

**FR-2.4.2** Страница сравнения — таблица: строки = характеристики, столбцы = товары.

**FR-2.4.3** Для неавторизованных пользователей сравнение хранится на устройстве (браузер). При авторизации сравнение переносится в аккаунт.

**FR-2.4.4** Пользователь должен иметь возможность удалять товары из сравнения.

### 2.5. Избранное

**FR-2.5.1** Пользователь должен иметь возможность отмечать товары как «избранное».

**FR-2.5.2** Для неавторизованных избранное хранится на устройстве (браузер). При авторизации избранное переносится в аккаунт (объединяется с уже сохранённым).

**FR-2.5.3** Авторизованный пользователь должен иметь возможность просматривать список избранного в личном кабинете.

**FR-2.5.4** Пользователь должен иметь возможность удалять товары из избранного.

## 3. Комплекты

**FR-3.1** Пользователь должен иметь возможность собрать комплект: выбрать шину и диск, указать количество (по умолчанию 4).

**FR-3.2** Система должна проверять совместимость выбранных шины и диска (типоразмер диска должен соответствовать типоразмеру шины).

**FR-3.3** Система должна отображать состав комплекта и общую цену.

**FR-3.4** Пользователь должен иметь возможность добавить готовый комплект в корзину одним действием (в корзину добавляется 4 шины + 4 диска).

---

## 4. Корзина

**FR-4.1** Корзина привязывается к сессии браузера (для гостя) или к аккаунту (для авторизованного).

**FR-4.2** При авторизации корзина гостя объединяется с корзиной аккаунта (если есть).

**FR-4.3** Пользователь должен иметь возможность:
- просматривать содержимое корзины
- добавлять товар (с указанием типа товара, ID и количества)
- изменять количество товара
- удалять товар из корзины

**FR-4.4** Пользователь должен иметь возможность запросить предварительный расчёт стоимости доставки — система рассчитывает стоимость на основе региона, веса/габаритов товаров и выбранного способа доставки.

**FR-4.5** Пользователь должен иметь возможность зарезервировать текущие цены на N минут (N задаётся в конфигурации, по умолчанию 30). Во время резерва цены не меняются.

---

## 5. Оформление и оплата заказа

### 5.1. Создание заказа

**FR-5.1.1** Пользователь должен иметь возможность оформить заказ из текущей корзины.

**FR-5.1.2** При оформлении заказа пользователь указывает:
- способ доставки: самовывоз / курьер / транспортная компания
- адрес доставки (из адресной книги или новый)
- способ оплаты: карта онлайн / СБП / наличные / безналичный расчёт (для юрлиц)
- контактные данные: имя, телефон, email
- комментарий к заказу (опционально)

**FR-5.1.3** Система при создании заказа должна проверить:
- наличие товаров на складах (достаточное количество)
- актуальность цен (сверка с зарезервированными, если был резерв)

**FR-5.1.4** После создания заказа:
- если оплата онлайн — система должна сформировать ссылку для перехода на платёжный шлюз
- заказ получает статус в соответствии с этапом обработки

### 5.2. Статусная модель

**FR-5.2.1** Заказ должен проходить следующие статусы:
- `Новый` — создан, ожидает оплаты
- `Оплачен` — оплата получена
- `В обработке` — менеджер подтвердил, собирается
- `В доставке` — передан перевозчику
- `Доставлен` — получен пользователем
- `Отменён` — отменён до передачи в доставку (клиентом или менеджером)
- `Возврат` — возврат средств после доставки

### 5.3. Отмена заказа

**FR-5.3.1** Пользователь должен иметь возможность отменить заказ, пока он не передан в сборку/отгрузку (статусы: новый, оплачен).

### 5.4. Просмотр заказа

**FR-5.4.1** Пользователь должен иметь возможность просматривать статус и детали заказа: состав, сумма, статус оплаты и доставки, трек-номер (если присвоен).

## 6. Аутентификация и личный кабинет

### 6.1. Аутентификация

**FR-6.1.1** Гость должен иметь возможность зарегистрироваться по email и паролю.

**FR-6.1.2** Зарегистрированный пользователь должен входить по email и паролю, получая токен для авторизованных запросов.

**FR-6.1.3** Пользователь должен иметь возможность выйти из системы (инвалидация токена).

**FR-6.1.4** Пользователь должен иметь возможность восстановить пароль через email.

### 6.2. Профиль

**FR-6.2.1** Пользователь должен иметь возможность просматривать и редактировать профиль: ФИО, телефон, email.

### 6.3. Адресная книга

**FR-6.3.1** Пользователь должен иметь возможность сохранять несколько адресов доставки.

**FR-6.3.2** Пользователь должен иметь возможность добавлять и удалять адреса.

**FR-6.3.3** При оформлении заказа пользователь должен иметь возможность выбрать адрес из адресной книги.

### 6.4. История заказов

**FR-6.4.1** Пользователь должен иметь возможность просматривать список своих заказов с фильтром по статусу.

**FR-6.4.2** Пользователь должен иметь возможность открыть детали любого заказа.

**FR-6.4.3** Пользователь должен иметь возможность повторить заказ — корзина автоматически заполняется товарами из выбранного заказа.

### 6.5. Гараж

**FR-6.5.1** Пользователь должен иметь возможность добавлять автомобиль в гараж (марка, модель, год, модификация).

**FR-6.5.2** Пользователь должен иметь возможность просматривать список сохранённых автомобилей.

**FR-6.5.3** Пользователь должен иметь возможность удалять автомобиль из гаража.

**FR-6.5.4** Для каждого автомобиля в гараже система должна предоставлять:
- подбор совместимых шин и дисков (быстрый переход к каталогу с предустановленным фильтром)
- историю покупок, сделанных для этого автомобиля

---

## 7. Акции

**FR-7.1** Система должна предоставлять список активных акций (название, описание, срок действия, тип скидки).

**FR-7.2** Для каждой акции система должна показывать список товаров, участвующих в акции, с ценами со скидкой.

**FR-7.3** В каталоге и на карточке товара цена должна отображаться с учётом активной акции (если товар участвует).

**FR-7.4** Типы акций: процентная скидка, фиксированная скидка, подарок, специальная цена.

## 8. SEO и контент

### 8.1. Посадочные страницы каталога (landing pages)

**FR-8.1.1** Каждая комбинация фильтров в каталоге должна иметь канонический ЧПУ-адрес (человеко-понятный URL), а не только query-параметры. Система должна автоматически формировать URL по типу `/tires/205-55-r16`, `/tires/winter`, `/tires/michelin-205-55-r16`.

**FR-8.1.2** Система должна поддерживать статические посадочные страницы для популярных комбинаций фильтров: типоразмеры, сезоны, бренды, ценовые диапазоны, а также их комбинации.

**FR-8.1.3** Для каждой посадочной страницы каталога система должна возвращать SEO-поля: заголовок (title), H1, мета-описание (description), canonical URL, хлебные крошки (breadcrumbs).

### 8.2. SEO-тексты на страницах каталога

**FR-8.2.1** В нижней части каждой посадочной страницы каталога должен выводиться текстовый блок с уникальным содержанием (если он задан).

**FR-8.2.2** Система должна поддерживать назначение SEO-текстов по правилам:
- каждое правило содержит привязку к комбинации фильтров (тип товара, ширина, профиль, диаметр, сезон, бренд, цена от/до — любое подмножество полей)
- поля текстового блока: H1, title, meta-description, основной текст (HTML или markdown), приоритет
- если для текущего набора фильтров подходят несколько правил — показывается правило с наибольшим приоритетом

**FR-8.2.3** Если для страницы не назначено ни одного правила, система должна автоматически генерировать SEO-поля на основе текущих параметров фильтра (без основного текста).

**FR-8.2.4** Управление SEO-текстами должно осуществляться через административный интерфейс (создание, редактирование, удаление правил).

### 8.3. Бренды

**FR-8.3.1** Система должна предоставлять страницу со списком брендов (логотип, название, описание).

**FR-8.3.2** Система должна предоставлять страницу конкретного бренда с описанием и списком товаров этого бренда в каталоге.

### 8.4. Статьи и справочники

**FR-8.4.1** Система должна предоставлять список статей/блога и содержимое каждой статьи.

**FR-8.4.2** Система должна предоставлять справочник терминов по шинам и дискам.

### 8.5. Микроразметка

**FR-8.5.1** Для каждого товара система должна генерировать JSON-LD микроразметку schema.org/Product для поисковых систем.

## 9. Технические ограничения

**FR-9.1** Публичные эндпониты — не более 60 запросов в минуту с одного IP.

**FR-9.2** Авторизованные пользователи — не более 120 запросов в минуту.

**FR-9.3** Для неавторизованных пользователей идентификация гостевой корзины, избранного и сравнения производится по `device_id`, который генерируется на фронтенде.

**FR-9.4** Ошибки возвращаются в едином формате: сообщение об ошибке + детали (если нужно).

**FR-9.5** Валидация входных данных выполняется на серверной стороне перед любой бизнес-логикой.
