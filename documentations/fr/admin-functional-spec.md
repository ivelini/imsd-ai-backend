# Функциональные требования — Административная панель

> **Основание:** ТЗ административной панели (`tz/admin-functional-spec.md`)
> **Версия API:** `/api/admin` — `auth:sanctum`
> **Роли:** Главный администратор, Контент-менеджер, Менеджер по заказам, Складской менеджер

---

## 1. Аутентификация и роли

### 1.1. Вход в панель

**ADM-1.1.1** Администратор входит по email и паролю. Система выдаёт Sanctum-токен с ограниченным сроком действия.

**ADM-1.1.2** Сессия администратора должна автоматически завершаться после периода бездействия (по умолчанию 60 минут).

### 1.2. Роли и права

**ADM-1.2.1** Система должна поддерживать минимум 4 роли с разными правами:
- Главный администратор — полный доступ ко всем разделам и управление администраторами
- Контент-менеджер — каталог, бренды, SEO-тексты, статьи, справочники, акции
- Менеджер по заказам — заказы, клиенты
- Складской менеджер — остатки, цены, склады, поставщики

**ADM-1.2.2** Каждый эндпоинт должен проверять права текущего администратора. При отсутствии прав — возвращать ошибку 403.

---

## 2. Дашборд

**ADM-2.1** При входе в панель система должна отображать сводку ключевых показателей:
- количество новых заказов (сегодня / за неделю / за месяц)
- выручка (сегодня / за неделю / за месяц)
- заказы по статусам с количеством
- последние 10 заказов (ссылка на карточку заказа)
- топ-10 товаров по продажам за месяц
- товары с остатком ниже порогового значения (настраивается)
- количество активных акций

**ADM-2.2** Показатели дашборда должны обновляться при перезагрузке страницы. Кэширование тяжёлых расчётов (выручка, топ-10) — до 15 минут.

---

## 3. Управление каталогом

### 3.1. Список товаров

**ADM-3.1.1** Система должна отображать таблицу всех товаров с колонками: ID, фото, название/артикул, бренд, тип (шина/диск), цена, остаток, статус публикации, дата создания.

**ADM-3.1.2** Доступны фильтры: тип товара, бренд, статус публикации, дата создания (диапазон). Поиск: по названию, артикулу, EAN.

**ADM-3.1.3** Результаты пагинируются (по умолчанию 50 на странице). Доступна сортировка по каждому столбцу.

### 3.2. Редактирование товара

**ADM-3.2.1** Система должна предоставлять форму редактирования товара с разделением на группы полей в зависимости от типа товара.

**Для шины (ADM-3.2.2):**
- Бренд (выпадающий список)
- Ширина, профиль, диаметр (числовые поля)
- Сезон (выпадающий список: зима/лето/всесезон)
- Шипы (да/нет)
- Индекс скорости, индекс нагрузки (текстовые поля)
- Run-flat (да/нет)
- XL / усиленная (да/нет)
- Год выпуска (число)
- EAN (текст)
- Описание (textarea с форматированием)
- Статус публикации (опубликовано / черновик)
- Метки: «Хит продаж», «Новинка»

**Для диска (ADM-3.2.3):**
- Бренд (выпадающий список)
- Тип (литой / штампованный / кованый)
- Цвет
- PCD, ET, DIA, ширина, диаметр (числовые поля)
- EAN (текст)
- Описание (textarea с форматированием)
- Статус публикации
- Метки: «Хит продаж», «Новинка»

**ADM-3.2.4** Изменения должны сохраняться по кнопке «Сохранить». Возможен частичный ввод — система валидирует обязательные поля.

### 3.3. Изображения товара

**ADM-3.3.1** Для каждого товара можно загрузить несколько изображений (до 10).

**ADM-3.3.2** Первое изображение считается главным. Порядок можно менять перетаскиванием.

**ADM-3.3.3** Поддерживаемые форматы: JPEG, PNG, WebP. Максимальный размер файла — 10 МБ. При загрузке система автоматически создаёт миниатюры для списка.

**ADM-3.3.4** Изображения можно удалять по одному.

### 3.4. Импорт товаров

**ADM-3.4.1** Администратор может загрузить XLSX-файл с товарами. Система сопоставляет колонки файла с полями товара.

**ADM-3.4.2** При импорте система проверяет:
- Формат файла (только XLSX)
- Обязательные поля (не менее 80% заполненных строк)
- Уникальность EAN (если указан)

**ADM-3.4.3** Система показывает результат импорта: сколько строк добавлено, сколько обновлено, сколько пропущено с ошибками, список ошибок построчно.

**ADM-3.4.4** При повторном импорте строки с совпадающим EAN обновляются, новые — добавляются.

### 3.5. Бренды

**ADM-3.5.1** Система должна предоставлять CRUD для брендов: название, slug (генерируется автоматически из названия), логотип (изображение), описание, тип (шины / диски / оба), статус публикации.

**ADM-3.5.2** При удалении бренда система должна проверять, есть ли товары этого бренда. Если есть — блокировать удаление с сообщением о количестве привязанных товаров.

---

## 4. Остатки и цены

### 4.1. Склады (крупные продавцы)

**ADM-4.1.1** Система должна предоставлять CRUD для складов — это крупные продавцы/дистрибьюторы, у которых мы покупаем товар. Поля склада: название (обязательное).

**ADM-4.1.2** Для каждого товара должна отображаться таблица остатков по складам: склад, количество, закупочная цена, цена продажи.

**ADM-4.1.3** Администратор должен иметь возможность изменить количество, закупочную цену и цену продажи для каждого склада.

**ADM-4.1.4** Система должна хранить историю изменений цен и остатков: дата, старое значение, новое значение, кто изменил.

**ADM-4.1.5** Импорт остатков и цен из XLSX-файла (прайс от склада) — загрузка, сопоставление колонок, обновление остатков.

### 4.2. Правила наценки

**ADM-4.2.1** Система должна предоставлять CRUD для правил наценки по складам. Поля правила: склад, цена от, цена до, коэффициент.

**ADM-4.2.2** Один склад может иметь несколько правил для разных диапазонов закупочных цен.

**ADM-4.2.3** При импорте прайса (XLSX) система должна для каждой строки:
- найти подходящее правило наценки для склада по диапазону закупочной цены
- рассчитать цену продажи: `purchase_price × coefficient`
- сохранить и закупочную цену (`purchase_price`), и цену продажи (`price`)

**ADM-4.2.4** Если подходящее правило наценки не найдено, цена продажи устанавливается равной закупочной.

**ADM-4.2.5** Цену продажи можно переопределить вручную после авторасчёта (например, для округления или спецпредложения). При ручной правке цена больше не пересчитывается при повторном импорте, пока не будет сброшена вручную.

### 4.3. Поставщики (заводы-производители)

**ADM-4.3.1** Система должна предоставлять CRUD для поставщиков: название, код. Внутренний справочник, клиент не видит.

**ADM-4.3.2** Каждый товар привязан к одному поставщику. Один бренд — один поставщик.

---

## 5. Управление заказами

### 5.1. Список заказов

**ADM-5.1.1** Система должна отображать таблицу заказов: номер, дата, клиент (имя/телефон), сумма, статус, способ оплаты, способ доставки.

**ADM-5.1.2** Фильтры: по статусу, дате (диапазон), клиенту (поиск по имени/телефону/email), по сумме (диапазон), по способу доставки/оплаты.

**ADM-5.1.3** Сортировка по любому столбцу. Пагинация.

### 5.2. Карточка заказа

**ADM-5.2.1** Система должна отображать полную информацию о заказе:
- Номер заказа и дата создания
- Состав: товары, количество, цена за единицу, общая сумма по позиции
- Контактные данные клиента (имя, телефон, email)
- Адрес доставки
- Способ доставки и стоимость
- Способ оплаты и статус оплаты
- Комментарий клиента (если есть)
- История изменений статуса: дата, старый статус, новый статус, кто изменил

### 5.3. Действия с заказом

**ADM-5.3.1** Менеджер может перевести заказ в следующие статусы:

| Текущий статус | Доступные действия | Результат |
|----------------|-------------------|-----------|
| Новый / Оплачен | Подтвердить | В обработке |
| Новый / Оплачен | Отменить | Отменён |
| В обработке | Передать в доставку | В доставке |
| В обработке | Отменить | Отменён |
| В доставке | Отметить доставленным | Доставлен |
| В доставке | Оформить возврат | Возврат |
| Доставлен | Оформить возврат | Возврат |

**ADM-5.3.2** При переводе в статус «В доставке» менеджер указывает: транспортная компания, трек-номер.

**ADM-5.3.3** При отмене заказа менеджер указывает причину отмены.

**ADM-5.3.4** Каждое изменение статуса должно фиксироваться в истории с указанием даты и администратора.

### 5.4. Уведомления

**ADM-5.4.1** При создании нового заказа ответственный менеджер получает уведомление в панели.

**ADM-5.4.2** При изменении статуса заказа клиент получает email-уведомление (с информацией о новом статусе).

---

## 6. Клиенты

### 6.1. Список клиентов

**ADM-6.1.1** Система должна отображать таблицу зарегистрированных пользователей: ID, имя, телефон, email, дата регистрации, количество заказов, общая сумма покупок.

**ADM-6.1.2** Фильтры: по дате регистрации (диапазон), по наличию заказов. Поиск: по имени, телефону, email.

### 6.2. Карточка клиента

**ADM-6.2.1** Система должна отображать профиль клиента:
- Контактные данные
- Дату регистрации
- Список заказов (с возможностью перейти в карточку заказа)
- Сохранённые адреса
- Автомобили в гараже
- Общая сумма и количество покупок

---

## 7. Акции

### 7.1. Управление акциями

**ADM-7.1.1** Система должна предоставлять CRUD для акций.

**ADM-7.1.2** Поля акции: название, описание, тип (процент / фиксированная сумма / подарок / спеццена), значение скидки, дата начала, дата окончания, приоритет.

**ADM-7.1.3** Акция активна, если текущая дата/время находятся между `starts_at` и `ends_at`. Статусов нет.

**ADM-7.1.4** Привязка товаров к акции:
- можно выбрать конкретные товары (по одному)
- можно выбрать все товары бренда
- можно выбрать все товары каталога

**ADM-7.1.5** Если на товар действует несколько активных акций одновременно, применяется та, что привязана к более конкретному объекту: конкретный товар → бренд → весь каталог. Внутри одной категории — с наибольшей скидкой.

**ADM-7.1.6** Акция отображается в каталоге и на карточке товара только в период между датой начала и окончания.

---

## 8. SEO-тексты каталога

### 8.1. Управление правилами

**ADM-8.1.1** Система должна предоставлять CRUD для правил показа SEO-текстов на страницах каталога.

**ADM-8.1.2** Поля правила:
- тип товара (шины / диски / оба)
- набор фильтров привязки (ширина, профиль, диаметр, сезон, бренд, шипы, цена от/до — любое подмножество; если поле не указано — означает «любое значение»)
- H1 (текст)
- Meta-title (текст; если не указан — используется H1)
- Meta-description (текст)
- Основной текст (с поддержкой форматирования)
- Приоритет (целое число; чем выше — тем важнее)
- Статус (активно / неактивно)

**ADM-8.1.3** Если для набора фильтров подходят несколько правил, применяется правило с наибольшим приоритетом.

**ADM-8.1.4** Система должна показывать превью того, как страница будет выглядеть с выбранным правилом.

**ADM-8.1.5** Список правил отображается в виде таблицы с фильтрацией по типу товара и статусу.

---

## 9. Контент

### 9.1. Статьи

**ADM-9.1.1** Система должна предоставлять CRUD для статей: заголовок, slug (автогенерация с возможностью ручного ввода), анонс, полный текст (с форматированием), изображение, дата публикации, категория, статус (черновик / опубликована).

**ADM-9.1.2** Категории статей: сезонные советы, подбор, новости.

**ADM-9.1.3** SEO-поля для статьи: meta-title, meta-description.

### 9.2. Справочник терминов

**ADM-9.2.1** Система должна предоставлять CRUD для терминов глоссария: термин, определение, категория (шины / диски / общее).

### 9.3. Страницы брендов

**ADM-9.3.1** При редактировании бренда (см. ADM-3.5.1) администратор может указать описание, которое отображается на странице бренда.

---

## 10. Регионы, склады, доставка

### 10.1. Регионы и города

**ADM-10.1.1** Система должна предоставлять CRUD для регионов и городов: название, сортировка (порядок отображения в виджете выбора города).

### 10.2. Наценка по городам

**ADM-10.2.1** Система должна предоставлять CRUD для правил наценки по городам. Поля правила: город, цена от, цена до, наценка (фиксированная сумма в рублях).

**ADM-10.2.2** Один город может иметь несколько правил для разных диапазонов цены товара (stocks.price).

**ADM-10.2.3** При отображении каталога и карточки товара система должна для выбранного города:
- найти подходящее правило по диапазону stocks.price
- рассчитать финальную цену: `stocks.price + city_markup`
- показать клиенту финальную цену

**ADM-10.2.4** Если для города правило не найдено — наценка 0, финальная цена = stocks.price.

### 10.3. Склады

**ADM-10.3.1** Система должна предоставлять CRUD для складов — это крупные продавцы/дистрибьюторы, у которых мы покупаем товар. Поля склада: название (обязательное). Склад не имеет физического адреса — это не точка выдачи.

### 10.4. Точки выдачи

**ADM-10.4.1** Система должна предоставлять CRUD для точек выдачи — физических адресов, где клиенты забирают товар (самовывоз). Поля: город, адрес, контакты, режим работы.

### 10.5. Коэффициенты доставки

**ADM-10.5.1** Система должна предоставлять CRUD для коэффициентов доставки: цена от/до, тип товара, коэффициент (множитель для расчёта стоимости).

**ADM-10.5.2** Расчёт доставки: стоимость товара × коэффициент.

### 10.6. График отгрузки

**ADM-10.6.1** Система должна предоставлять CRUD для графика отгрузки по складам: склад, день недели, время отсечки (до какого времени заказ принимается для отгрузки в этот день), количество дней до отгрузки, количество дней после.

### 10.7. Сроки доставки по городам

**ADM-10.7.1** Система должна предоставлять CRUD для времени доставки по городам: город, количество рабочих дней (из Челябинска до города).

**ADM-10.7.2** Если для города время не задано — при расчёте срока доставки используется значение по умолчанию (настраивается в конфиге).

---

## 11. Администраторы

**ADM-11.1** Система должна предоставлять CRUD для администраторов (доступно только главному администратору).

**ADM-11.2** Поля: имя, email, пароль, роль (главный / контент-менеджер / менеджер по заказам / складской), статус (активен / заблокирован).

**ADM-11.3** При блокировке администратора его текущий токен должен инвалидироваться.

---

## 12. Автомобили и совместимость

### 12.1. Справочник автомобилей

**ADM-12.1.1** Система должна предоставлять CRUD для марок, моделей и модификаций автомобилей: название, год выпуска от/до, объём двигателя, тип двигателя, мощность, комплектация.

### 12.2. Совместимость

**ADM-12.2.1** Система должна предоставлять интерфейс для управления совместимостью: выбор модификации автомобиля → привязка типоразмеров шин (ширина, профиль, диаметр) и спецификаций дисков (PCD, ET, DIA, ширина, диаметр).

**ADM-12.2.2** Тип совместимости: родной (OEM) / замена / тюнинг.

**ADM-12.2.3** Одна модификация может иметь несколько типоразмеров (разные комплектации, опции).

**ADM-12.2.4** Система должна поддерживать импорт совместимости из CSV/XLSX: колонки «модификация → типоразмер → тип совместимости».

---

## 13. Технические ограничения

**ADM-13.1** Все эндпоинты админ-панели защищены аутентификацией (Sanctum).

**ADM-13.2** При отсутствии прав на действие — HTTP 403.

**ADM-13.3** Формат ответов — единый: `{ data: ... }` для успеха, `{ message: ..., errors: ... }` для ошибок.

**ADM-13.4** Rate limiting для админ-панели — 120 запросов в минуту.

**ADM-13.5** Валидация входных данных — в FormRequest (стандартный паттерн проекта).
