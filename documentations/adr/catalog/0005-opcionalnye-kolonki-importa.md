# 0005. Опциональные колонки импорта — отдельные механики с флагами присутствия

- **Статус:** Accepted
- **Дата:** 2026-08-21
- **Связанные ADR:** 0006 (SEO-формула slug), 0007 (описание на модели)

## Контекст

В файлы импорта приходят новые данные не единовременно: колонки `origin_*` и `description` появляются раньше у дисков, чем у шин, и могут вовсе отсутствовать. При этом основной импорт (товары, остатки, цены) должен работать всегда — иначе один «недокомплектный» файл останавливает поставку каталога.

## Решение

Опциональные колонки обрабатываются отдельной механикой, не встроенной в обязательный конвейер: каждая строка несёт флаг присутствия (`origin_present`, `description_present`) — колонка была в файле (ключ есть в данных), даже если значение пустое. Флаг есть → механика активна, значение пишется (включая null). Флага нет → поле сущности (origin_id, description модели) не трогается при реимпорте. Парсинг значений — чистые функции (OriginParser), мусор → null, в БД не попадает.

## Почему (альтернативы)

- **Сделать origin/description обязательными колонками** — ломает импорт файлами без них (шины ещё без `description`), противоречит цели.
- **Вести «наличие колонки» по значению (null = нет)** — нельзя отличить «колонки не было» от «колонка была, но пустая»; пустая колонка обязана сбрасывать значение, отсутствующая — сохранять прежнее.
- **Переоткрывать вопрос при каждой новой опциональной колонке** — паттерн уже повторён дважды (origin, description), фиксируем один подход.

## Последствия

Проще: новые опциональные данные добавляются по шаблону (парсер + резолвер + флаг), основной импорт не знает об их существовании. Сложнее: DTO несут сервисные флаги; при реимпорте без колонок старое значение остаётся висеть (осознанно — механике нет, чистить некому). Пересмотрим, если появится требование «отсутствие колонки = очистка»: тогда флаг станет избыточным, значение будет писаться безусловно.
