# 0012. Домен Booking в монолите — перенос сервиса записи из tireslot

- **Статус:** Accepted
- **Дата:** 2026-09-11
- **Связанные ADR:** 0008

## Контекст

Запись на шиномонтаж развивалась отдельным сервисом tireslot (монолит Livewire, своя БД, свои ADR 0001–0010). Клиент магазина шин и клиент записи — один человек: два сервиса дублируют клиентов, панели и инфраструктуру. Перенос в монолит backend — развилка: что делать с публичным Livewire-визардом, где живёт клиент, как отделять таблицы домена.

## Решение

Booking — домен монолита backend (план: `.claude/plans/migration-tireslot-to-backend.md`):

- публичный UI записи — SPA (репо frontend) через `/api/booking`; Livewire-визард не переносится;
- клиент — единая `users` (+ `phone`, `email`/`password` nullable), `bookings.user_id`;
- таблицы домена — с префиксом `booking_`; `settings` — системный KV монолита без префикса;
- админка — кластер Filament в существующей панели (ADR 0008);
- код адаптируется под слои backend: Actions `execute(DTO)`, Preconditions, Backed Enum.

## Почему (альтернативы)

- **Перенести Livewire-визард в монолит:** дешевле, но второй фронт-стек рядом со SPA и рассинхрон с конвенцией «публичное — через API».
- **Оставить tireslot сервисом:** двойная поддержка identity, панелей, деплоя.
- **Отдельная таблица `customers`:** два клиента одного человека в одном монолите.

Цена: рерайт UI-слоя записи в SPA (вне backend), адаптация переносимого кода под слои монолита.

## Последствия

Проще: один клиент, одна панель, одна БД, один деплой. Сложнее: маппинг имён при переносе (`booking_`-префиксы, `BookingItem` вместо pivot-имени), визард в SPA — отдельный план. Пересмотрим: если Livewire станет основным фронтом монолита — вернём визард.
