# 0004. В кеш — сериализованные массивы: JSON-roundtrip ресурсов

- **Статус:** Accepted
- **Дата:** 2026-08-19
- **Связанные ADR:** 0003 (инвалидация кеша индексом ключей)

## Контекст

Публичный листинг шин кешируется (кеш до Action, правило проекта). Первая версия сериализовала payload через `JsonResource::collection(...)->resolve()`. `resolve()` не рекурсивный: вложенные Resource (`brand`, `images`) остаются объектами в массиве и уходят в database-кеш как есть; при `unserialize` они оживают как `__PHP_Incomplete_Class` — первый запрос корректный, последующие отдают мусор из кеша.

## Решение

В кеш кладётся только сериализованный массив, развёрнутый JSON-roundtrip'ом: `json_decode(Resource::collection(...)->toJson(), true)`. `json_encode` рекурсивно разворачивает `JsonSerializable` (вложенные Resource, коллекции) — в отличие от `resolve()`. Схема ключа кеша версионируется (`tire-list:v2:...`): смена формата payload инвалидирует старые ключи без ручной очистки.

## Почему (альтернативы)

- **Кешировать объекты Resource / пагинатор с моделями** — готовый ответ, но `serialize`/`unserialize` ломает объекты с зависимостями (автозагрузка при десериализации, связи моделей не восстанавливаются) — противоречит правилу «в кеш только массивы/скаляры».
- **`resolve()` по каждому уровню вручную** — требует знания структуры каждого ресурса в месте кеширования, хрупко при добавлении вложенных Resource.
- **Не кешировать листинг** — отказ от выгоды; кеш нужен по правилу «кеш до Action».

## Последствия

Проще: payload из кеша — всегда чистый массив, формат гарантирован JSON'ом; тест-контракт — кеш-hit проверяет валидную структуру, а не только 0 запросов БД. Сложнее: JSON-roundtrip теряет типы, не представимые в JSON (объекты, бинарные данные), — для API-ответов приемлемо. Пересмотрим при добавлении не-JSON-типов в ответ: версионировать ключ и менять сериализатор.
