## Решение

Админка переезжает с React SPA (отдельный репозиторий, не в проде) на Filament-панель внутри backend: мотив — скорость будущих CRUD-разделов FR (заказы, клиенты, статьи, авто, роли). Admin API (`/api/admin/*`) удаляется вместе с переносом разделов, React замораживается. Волны: 0 каркас → 1 справочники → 2 товары → 3 новые разделы → 4 зачистка (план: `.claude/plans/filament-migration.md`).

## Каркас (волна 0)

- Панель `/panel` (id `admin`), Filament 5.x, `AdminPanelProvider` в `app/Providers/Filament/`.
- Auth: session-guard `admin` (provider `admins` → `App\Models\Auth\Admin`); `Admin implements FilamentUser` — доступ только активным (`is_active`). Sanctum-токены остаются, пока жив admin API.
- Роли: enum `AdminRoleCode` (super-admin, content-manager, order-manager, warehouse-manager), сиды ролей — из enum. Доступ к ресурсам — через policies (`App\Policies\AdminPolicy`: администраторы — только super-admin). spatie не используется.
- Уведомления: нативные Filament (`->databaseNotifications()`; в v4 трейта нет — включение методом панели); `NotificationResource` над таблицей `notifications` с действием `markAsRead`.

## Политика слоёв (контракт для всех ресурсов)

- Чтение — Eloquent + скоупы моделей; Actions чтения API не переносятся.
- Запись доменных сущностей — только через существующие Actions, Preconditions — перед мутацией.
- Прямой Eloquent-записи ресурсами нет: иначе ломаются SEO-slug, пересчёт `catalog_prices`, инвалидация кеша Observer'ами.

## Волна 1 — справочники (закрыта)

Экран переносится: Filament-ресурс (форма/таблица) → приёмка → снос API-среза (маршрут, контроллер, Request/Resource, Action чтения; Precondition переиспользуется панелью; Observer остаётся — инвалидация срабатывает на записи из формы). Bulk-delete не используется там, где удаление под Precondition (массовое удаление обходило бы проверку).

**1a — Brand (готово):** `BrandResource`; delete через `EnsureBrandHasNoProducts` (danger-нотификация); срезаны маршрут/контроллер/Request/Resource/GetBrandList. `BrandBriefResource` прожил до волны 2b — вложен в API Tire/Wheel (снесён вместе с ними). Тесты: BrandResourceTest (7) + BrandApiRemovalTest (404).

**1b — партия справочников (готово):** Warehouses, WarehouseMarkupRules, DeliverySchedules, CityPriceRules, DeliveryPoints (CRUD) + Cities, Countries (read-only: `canCreate/canEdit/canDelete = false`, только List). Детали: день недели — Select со скалярными значениями `WeekDay` (модель кастует integer), `TimePicker->seconds(false)` ('H:i' в БД); `WeekDay::label()` добавлен. Удаление партии — стандартный DeleteAction (Precondition'ов нет). Снесены маршруты/контроллеры/Request'ы/Resources/Actions чтения 7 разделов. Тесты: 19 ресурсных + DirectoryApiRemovalTest (7 × 404).

**1c — ProductModel (готово, волна 1 закрыта):** slug unique в рамках brand_id (`modifyRuleUsing → where('brand_id', …)`); type — скалярные опции (модель без enum-каста); image FileUpload; delete с `EnsureModelHasNoProducts`. Инвалидация references вынесена из контроллера в **ProductModelObserver** (saved/deleted) — единый механизм с BrandObserver. Снесён API-срез /models. `ProductModelBriefResource` прожил до волны 2b.

**Итог волны 1:** 9 справочников на Filament; admin API справочников снесён полностью.

## Волна 2 — товары

**2a — Tire (готово):** TireProductResource (форма по TireProductRequest; model_id — только type=tire; Section/Grid из Filament\Schemas\Components); подготовка данных вынесена в **TireDataComposer** (name из модели + SEO-slug) — единая реализация для хуков страниц и контроллера. slug/euro_label/origin_id не редактируются. В списке шин действие строки одно — «Изменить»: удаление шины из списка убрано 2026-09-12 (у дисков `DeleteAction` сохранён — панель несимметрична).

**2b — Wheel + снос API товаров (готово):** WheelProductResource — зеркало Tire (model_id только type=wheel, `type` — Select WheelType со скалярными опциями через string-каст, геометрия width/diameter/pcd/et/hub_diameter с шагом 0.1 под `decimal:1`), подготовка данных — **WheelDataComposer** (name из модели + `ProductSlugService::wheel`). admin API товаров снесён целиком одной волной: маршруты `/tires*`, `/wheels*`, `/products`; 7 контроллеров; 9 Request'ов + концерны `ValidatesTireFilters`/`ValidatesWheelFilters`; 5 Resources — включая `BrandBriefResource`/`ProductModelBriefResource` (их единственными потребителями были Tire/Wheel API) и `CatalogProductResource`; Action'ы `GetTireDimensions`/`GetWheelDimensions`/`GetTireProductList`/`GetWheelProductList`/`GetCatalogProducts` с DTO. Панель — два раздельных ресурса вместо агрегированного `/products`. `GetWarehouseStock` (+Input/Result/`WarehouseStockRowResource`) сохранён без HTTP-потребителя: нужен волне 2d (RelationManager остатков), тест переведён на прямой вызов Action. Тесты: WheelResourceTest (9), TireWheelApiRemovalTest (6 × 404 + страж), кейс коллизии slug перенесён в TireResourceTest.

**2c — изображения (готово):** один `ImagesRelationManager` на оба товара (связь `images` морфная и идентична; зарегистрирован в `getRelations()` Tire и Wheel). FileUpload с `storeFiles(false)` — файл приходит `TemporaryUploadedFile` и сохраняется **доменным Action** `UploadImage`, не Filament'ом; порядок перетаскиванием — `ReorderImages` через хук `afterReordering` (встроенная SQL-запись Filament обошла бы слой). Прочие actions: `SetMainImage`, `DeleteImage`. Снесён Image API: 5 маршрутов, контроллер, 3 Request'а, admin-`ImageResource`, `ListImages`; удалён мёртвый `ImageService::getNextMainImageId`.

**PanelAction** (`app/Filament/Support/PanelAction.php`) — общий хелпер панельных действий: `PanelAction::run('Что сделано', fn () => ...)` — success-нотификация при успехе, danger с текстом `DomainException` при провале (Precondition). Введён по правилу «обобщай на третий раз» (Brands, ProductModels, изображения); те используются через него.

Фикс дефекта: `DeleteImage` удалял только запись в `images` — файл оставался на public-диске (сироты); теперь снимается и файл.

**2d (часть 1) — импорт (готово):** страница панели `/panel/import` (`ImportProducts`, реализует `HasTable`) — форма «тип + файл» (MIME-типы зависят от типа: XLSX для шин/дисков/моделей/точек, CSV для автомобилей) → `EnsureNoActiveImport` → `StartProductImport`; ниже таблица истории импортов с фильтром по типу и `poll('5s')`. **Пайплайн (Jobs, чанки, парсеры) не менялся** — сменилась только точка входа. Снесён Import API: 7 маршрутов, 7 контроллеров, 2 Request'а, `ProductImportResource`. Адрес уведомления о завершении переведён с `/admin/imports/{id}` (React-админка) на `/panel/import`.

**2d (часть 2) — остатки складов (готово; 2026-09-12 правка из панели убрана):** `StocksRelationManager` (общий для Tire/Wheel) — таблица остатков товара по складам (склад, количество, закупочная, продажная) **только для чтения**: действия «Добавить/Изменить/Удалить» удалены — остаток и цены пишет импорт (`UpsertStock` применяет наценку склада при записи остатка, ADR 0009), панель их не правит. До 2026-09-12 relation manager правил количество/закупочную/продажную (FR ADM-4.1.2/4.1.3; в старом API был только GET): ввод закупочной пересчитывал продажную по правилу наценки склада, её можно было перебить вручную; после сохранения звался `PopulateCatalogPrices` для затронутого остатка; удаление снимало зависимые `catalog_prices`. Попутно починен `PopulateCatalogPrices`: он считал наценку склада заново из `purchase_price` и затирал ручную продажную — теперь берёт готовую `stocks.price` (FR ADM-10.2.2/10.2.3). Снесены осиротевшие `GetWarehouseStock` (+DTO/Resource), `PriceCalculator::calculateFinalPrice`, `DeliveryTimeCalculator::calculate/calculateAll`.

**2d (часть 3) — акции (готово):** `PromotionResource` (`/panel/promotions`) — CRUD акций с привязкой «шина / диск / бренд / весь каталог». Попутно реализовано **применение скидок** (до волны акции создавались, но нигде не применялись): `PromotionDiscount` (percent/fixed/special меняют цену, gift — нет) и `PromotionMatcher` (приоритет товар → бренд → каталог, внутри — большая скидка) — обе чистые функции; скидка входит в `catalog_prices.price`, рядом хранится `base_price`. Границы действия акций закрывает плановая задача `promotions:sync` (каждые 5 минут; первая задача проекта). Листинги отдают `old_price` и `promotion`. Снесён API акций (5 маршрутов). ADR 0010.

**Осталось в admin API:** references, auth/notifications.

## Волна 2d/4 — цена и срок по выбранному городу в списке шин (готово)

`ListTireProducts` учился выбирать город: над таблицей — селект (`content()` + `EmbeddedTable`; штатные табы и RenderHook'и сохранены), состояние — Livewire-свойство `#[Url] $cityId`, то есть город живёт в URL (`?cityId=6`) и переживает перезагрузку/шаринг ссылки; дефолт в `mount()` — `config('shop.default_city')` («Челябинск»), несуществующий id трактуется как отсутствие города. Атрибут `#[Url]` Livewire применяет раньше `mount()`, поэтому дефолт ставится через `??=`.

Колонка «Цена в городе (Уфа)» в `TireProductsTable` — `12 800,00 ₽ — 5 дн. (наценка 300,00 ₽)`, три части независимы: **цена** — минимум `catalog_prices.price` по остаткам в наличии (как в листинге каталога), **наценка** — разница `base_price` и `stocks.price` той же строки снимка (у Челябинска правил нет — не выводится), **срок** — точный расчёт `DeliveryInfoService::enrichProduct()` на момент запроса. Без города колонки нет, без цены города — «Нет цены». Границы «снимок vs расчёт на лету» — ADR 0011.

Запрос листинга грузит `stocks.warehouse.deliverySchedules` и цены города одним `with()` (иначе N+1), сервис срока — один инстанс на рендер (кеш дней и правил города внутри). Порог склада `shop.delivery_min_quantity` здесь не участвует: срок берётся по остаткам товара, как на карточке.

### Смена города: конфигурацию таблицы приходится пересобирать

**Состояние страницы, прочитанное в `table()`/schema-классе, отстаёт на один рендер.** Livewire (`HandleComponents::update()`) сначала гидратирует компонент — и в этой фазе исполняется `bootedInteractsWithTable()`, который собирает и **кеширует** таблицу (`$this->table = $this->table($this->makeTable())`, `getTable()` — просто отдача кеша), — и только потом применяет обновлённые свойства. К моменту `render()` менять таблицу уже некому: `configure($table, $this->currentCity())` был вызван со старым `cityId` из снапшота.

Общая асимметрия Filament: **структура** таблицы (колонки, фильтры, заголовки) собирается на гидратации, а **данные** разрешаются лениво при рендере. Штатные `tableFilters`/`tableSearch`/`tableSort` работают именно потому, что читаются в момент построения запроса; город же зашит в структуру — в заголовок колонки и в замыкание `state()` — и попадает в кеш.

Лечится пересборкой в `updatedCityId()`: `$this->table = $this->table($this->makeTable())` + `flushCachedTableRecords()` + `resetPage()`.

- `resetTable()` (штатный API «сбросить таблицу») **не подходит**: он дополнительно вызывает `resetTableFiltersForm()`, который перезаписывает `$this->tableFilters` формой с дефолтами полей (нет дефолтов — пустой), — сбросил бы активные фильтры, а у листинга шин они есть с 2026-09-11.
- Ленивые замыкания (`fn () => $this->currentCity()` внутри `configure()`) — рабочий путь (колонки принимают `Closure` для `label()`, запрос строится при рендере), но **наличие** колонки решается жадно, и следующий, кто напишет `->label("...{$city->name}")` без замыкания, вернёт баг молча. Пересборка чинит класс целиком.
- `bootedInteractsWithTable()` вызывать руками нельзя — это lifecycle-хук: повторный прогон трогает session-состояние поиска/сортировки.

Тот же кеш даёт попутный краш: `TireProductsTable` вызывал `getRelation('delivery')` безусловно, а `DeliveryInfoService::enrichProduct()` выставляет связь только когда срок вычислим. Товар с остатками, но без расписаний у складов, ронял листинг с `Undefined array key "delivery"`; закрыто проверкой `relationLoaded()`.

Тесты — `TireProductsTableTest` (+6 кейсов, включая остаток без расписания) и `TireProductsCitySwitchTest` (переключение города; панель задаётся явно через `Filament::setCurrentPanel()`, HTTP-запроса нет). Опции селекта Filament отдаёт Alpine-атрибутом (`options: JSON.parse(...)`), не текстом: тест проверяет `assertSee('Уфа')` и связку `entangle('cityId'` — иначе браузерный выбор города молча перестал бы что-либо менять.

## Фильтры листинга шин — характеристики

Сезон, ширина, профиль, диаметр и шипы — штатные `SelectFilter` с `->filtersLayout(FiltersLayout::AboveContent)`: селекты рендерятся **над таблицей**, тем же видом, что городской селект.

**Правило выбора:** страничное свойство (как `cityId`) оправдано только там, где параметр меняет **состав колонок** — иначе таблицу приходится пересобирать в `updatedXxx`. Параметр, который лишь сужает выборку, отдаётся штатному фильтру: Filament сам ведёт состояние в `tableFilters` (свойство `#[Url]` у `ListRecords` → query string), сбрасывает страницу, применяет `where`, рисует кнопку сброса. Своего кода на жизненный цикл — ноль.

Опции размеров — из каталога (`distinct()` + `orderBy`, ключ = значение), включая неопубликованные товары: администратор ищет товар, а не витрину. `TireFacetAssembler::dimension()` не переиспользуется — он отдаёт значения контракта публичного API (`w205`, `r16`). Сезон — `->options(Season::class)`, все три кейса независимо от данных.

## Фильтры листинга слотов — период, состояние и клиенты

`/panel/booking/slots` (кластер «Шиномонтаж»): фильтр «Состояние» (Закрыт/Открыт) и фильтр «Период» — селект «Быстрый выбор» и два календаря «С»/«По» в одной строке, над таблицей (`AboveContent`). Пресеты — энум `SlotPeriod`: `today | tomorrow | current_week | current_month`. Границы считает чистая `SlotPeriod::range(now)` (приватный `spanRange()` — от начала первого дня до конца последнего): «Текущая неделя» — ISO-неделя пн–вс **целиком**, включая прошедшие её дни (не «от сегодня до воскресенья»), месяц — с 1-го по последнее число.

**Календаря с выделением диапазона у Filament нет** (в JS-бандле `date-time-picker.js` режима `range` нет вовсе), поэтому «дата или период» — это два поля: заполнено одно — один день (а не «от этой даты и дальше»), заполнены оба — диапазон включительно. Пресет заполняет обе даты, ручная правка любой даты снимает пресет; пусто — весь список.

**Фильтр периода общий на два листинга** — `App\Filament\Support\PeriodFilter::make(Closure $applyRange)` (рядом с `PanelAction`): схема с селектом и календарями, правило границ, бейдж активного периода и `weekDefaults()` для стартового состояния. Различается только сужение запроса: слоты — `whereBetween('date', …)`, записи — `whereHas('slot', …)`.

**Дефолт периода живёт на странице, а не в `->default()` фильтра.** Кнопка «Сбросить» перезаполняет форму фильтров дефолтами полей (`resetTableFiltersForm()` → `fill()`), поэтому с `->default()` сброс возвращал бы «Текущую неделю» вместо всего списка. Стартовый вид ставит страница: `$this->tableFilters['period'] ??= PeriodFilter::weekDefaults();`. Строка «Убрать все фильтры» (×) чистит состояние в null и без этого.

**Фильтры применяются сразу — `->deferFilters(false)`.** При дефолтной отложенной фильтрации форма живёт в `tableDeferredFilters`, а запрос читает `tableFilters`: быстрый выбор требовал бы второго клика, «Применить». По той же причине пресет — **поле** (`Select`), а не `Action`: действие пишет состояние на сервере мимо Livewire-хука `updated`, `resetPage()` не вызывается — оператор на 3-й странице, нажав «Сегодня», увидел бы пустую таблицу.

**Листинг записей** (`/panel/booking/bookings`) — тот же фильтр (`PeriodFilter` со `whereHas('slot')`: дата записи лежит в её слоте), тот же стартовый вид «текущая неделя», живая фильтрация, свои 50 строк и фильтры над таблицей (были спрятаны за кнопкой «Фильтры»). **Порядок строк исправлен** на «дата слота, затем время»: прежний `orderBy('start_time')` сортировал по времени суток без даты, и на недельном виде дни перемешивались. Дата слота берётся подзапросом (`Slot::select('date')->whereColumn('booking_slots.id', 'bookings.slot_id')`) — join не берём, он ломает выборки и `counts('items')`.

**Грабля: состояние селекта с энумом — кейс, не строка.** `Select`/`ToggleButtons` с `->options(Enum::class)` кастует состояние через `EnumStateCast`, поэтому `afterStateUpdated(fn (Set $set, ?string $state))` падает с `TypeError` — типизировать `?SlotPeriod $state`.

**Порядок — всегда хронология** (`date asc, hour asc`), от периода не зависит (в ходе ревью 2026-09-12 отказались от варианта «вся сетка — от дальней даты»). **Прошедшие дни срезает базовый запрос** — `where('date', '>=', now()->startOfDay())` в `modifyQueryUsing`: сетка хранит слоты истории (закрытые и с записями), в листинге они не нужны. Сравнение именно с началом дня: в колонке-дате время нулевое, и `>= now()` срезал бы весь сегодняшний день (см. граблю ниже). Следствие — «Текущая неделя» на практике показывает сегодня…воскресенье.

**Колонка «Состояние»** — `IconColumn` да/нет: открытый час зелёный круг (`CheckCircle`), закрытый красный (`XCircle`). До 2026-09-15 цвета были перевёрнуты (закрытый слот рисовался зелёной галочкой с подписью «Открыт»).

**Колонка «Клиенты»** заменила «Запись клиента» (`booking.user.name` — это запись, *закрывшая* слот, а не список записавшихся): строки «10:00 : Имя — телефон» (время начала из записи) по неотменённым записям слота, порядок по id, `with('bookings.user')` в `modifyQueryUsing` против N+1. Элементы списка Filament экранирует сам (`e()` в `TextColumn::render`) — `->html()` такой колонке не нужен, в отличие от колонки складов в листинге шин.

### Грабля: дата для `whereBetween` — Carbon, а не строка

Каст `date` пишет в SQLite `'2026-09-12 00:00:00'` (прод-Postgres приводит значение к дате сам), поэтому `whereBetween('date', ['2026-09-12', '2026-09-12'])` в тестах не находит ни одной строки, хотя в Postgres работает — расхождение тестовой и продовой БД. Границы передаются Carbon-объектами: Laravel форматирует их тем же `getDateFormat()` соединения, что и запись; в Postgres параметр без типа приводит `date` к дате, и индекс `UNIQUE(date, hour)` остаётся рабочим. Существующие обращения к этой колонке (`GenerateSlotGrid`) используют только нижнюю границу `where('date', '>=', 'Y-m-d')` — там сравнение строк случайно верно.

## Карточка слота: записи на слоте

Правка слота (`/panel/booking/slots/{slot}/edit`) — карточка дня: заголовок «Редактирование слота: 12.09.2026, 10:00» собирает `EditSlot::getTitle()` из даты и часа, а сами `date`/`hour` в `SlotForm` помечены `visibleOn('create')` — на правке остаются только «Слот закрыт» и «Причина закрытия» (слот уже связан с записями; перенос слота — отдельная механика ФТ-20).

Ниже вкладка «Записи» — `BookingsRelationManager` (через `SlotResource::getRelations()`): клиент и телефон, статус (badge), состав строками «Услуга — 2 шт» (`with('items.service')` против N+1) и сумма (`Money::formatted()`). «Добавить запись» — кнопка-ссылка на страницу создания записи с `?slot_id=<слот>`: форма создания остаётся одна и создаёт её тот же `CreateAdminBooking` (слот в форму подставляет `CreateBooking::fillForm()`); «Изменить» — `EditAction` со ссылкой на карточку записи; «Удалить» — обычный `DeleteAction`, правил перед удалением нет: привязка закрытия снимается FK-правилом (`booking_slots.booking_id` — `nullOnDelete`), слот остаётся закрытым и открывается кнопкой на сетке.

### Грабля: `Schema::getState()` в Filament 5 валидирует форму

На пустой форме бросает `ValidationException` — в `fillForm()` не годится. Подстановка состояния — `rawState([...$this->form->getRawState(), 'slot_id' => …])` (так же делает штатный `CreateRecord` для «создать ещё»); вариант `fill(['slot_id' => …])` теряет дефолты полей (`close_slot` = true).

### Грабля: денежный атрибут без поля в форме роняет страницу правки

Filament заполняет состояние формы `data` **всеми** атрибутами записи, поэтому `Money` уезжает в снапшот Livewire, а `Wireable` требует от payload массив (`WireableSynth` обходит его `foreach`, интерфейс `ArrayShapedSynth`). Так падала страница правки записи (`data.total_price`, 500 вместо карточки); страница услуги не падала только потому, что у `base_price` есть поле в форме. По проводу Money теперь `['kopecks' => N]` (подробнее — [Запись на шиномонтаж: домен Booking](booking-domain.md)).

### Грабля: `fake()->regexify()` с кириллицей выдаёт невалидный UTF-8

Faker режет многобайтный набор по байтам: `regexify('[АВЕКМНОРСТУХ]…')` возвращает битую последовательность, и сериализация состояния Livewire падает с `Malformed UTF-8 characters, possibly incorrectly encoded`. Госномер в `BookingFactory` собирается по частям из массива букв.

## Карточка записи: состав в форме и цена по прайсу

Правка записи (`/panel/booking/bookings/{id}/edit`) — рабочее место оператора по цене (ФТ-19): заголовок «Запись {дата слота}, {время}, {ФИО}, {телефон}» из `EditBooking::getTitle()` (дата слота — в заголовке, потому что поля «Слот» в форме нет), состав — **повторитель `items` в самой форме** (`->table()` + `TableColumn`: услуга / цена / количество), рядом «Итоговая стоимость» — `TextEntry` со `state()`.

**Грабля: устаревший `Placeholder` и его `content()`.** `Filament\Forms\Components\Placeholder` помечен `@deprecated` («Use `TextEntry` with the `state()` method instead»), но прямая замена `Placeholder::content(...)` на `TextEntry::content(...)` **молча ничего не рендерит**: `content()` у `TextEntry` — из `Schemas\Components\Text`, его view не используется, а `Placeholder::content()` работал только потому, что подменял собой `state()`. Рабочая замена — `TextEntry::make('x')->state(fn (Get $get) => ...)`.

**Одна схема состава на создании и правке** (2026-09-15): на создании — тот же повторитель строк с ценой и итогом, что на правке (прежний «Состав» с серверным пересчётом убран). Отличия форм остались только по делу: на создании телефон, на правке статус и причина отмены.

**Почему не relation manager.** Таблица состава в отдельном компоненте читает сохранённую запись и не видит несохранённый радиус: цена могла бы поменяться только после сохранения, да ещё и затерев ручную правку из модалки. Повторитель живёт в одном Livewire-компоненте с радиусом — цена пересчитывается на глазах. Прежний `ItemsRelationManager` удалён вместе с `getRelations()`.

**ФИО клиента — три поля.** В карточке записи (создание и правка) — «Фамилия», «Имя» (обязательны) и «Отчество» (как получится); на правке подставляются из карточки клиента и сохраняются в неё. Клиент показывается склейкой «Фамилия Имя Отчество» в заголовке, карточке слота и листингах; в списках поиск по клиенту идёт по частям (`whereHas('user', …)` — склейка не колонка).

**Причина отмены — по статусу.** Поле «Причина отмены» показывается только у статуса «Отменена» (и там обязательно); статус ушёл из «Отменена» — причина снимается, чтобы у завершённой записи не висела причина отмены.

**Слот в форме не выбирается** (2026-09-16): поля «Слот» нет ни на создании, ни на правке — на создании слот приходит адресом `?slot_id=` со страницы слота (кнопка «Добавить запись»), на правке берётся из записи, а дата видна в заголовке. Переноса записи на другой слот (ФТ-20) нет, поэтому поле на правке было обманчивым: время из чужого слота подставлялось, а слот не менялся. Номер слота при этом остаётся в **состоянии формы** (`rawState` в `CreateBooking::fillForm()`) — на нём варианты времени и подстановка начала часа (`BookingForm::slotHour()` читает `$get('slot_id')`); начало часа на создании проставляет страница.

**Время внутри часа.** Поле «Время» — Select с вариантами `11:00…11:59` по часу слота (на создании — слота из адреса, на правке — слота записи), состояние хранится как `HH:MM` и дегидратируется в `HH:MM:00`. Запись ровно на начало часа закрывает час; уехала внутрь часа — час освобождается. Чекбокса «Закрыть слот с привязкой к записи» в форме больше нет.

Механика: строки открываются снимком цены (`mutateFormDataBeforeFill` — рубли строкой; `dehydrateStateUsing` отдаёт `Money` при сохранении), `radius`/`car_type` с `->live()` и `afterStateUpdated` пересчитывают цену услуг **с прайс-правилами** (услуги без правил сохраняют снимок; нет комбинации — уведомление `DomainException`, цена не меняется), сохранение идёт через Action `UpdateAdminBooking`, а не `$record->update($data)`.

### Грабля: `Select` валидирует значение по своим опциям (`validation.in`)

Filament 5 добавляет правилу поля `in`: `Select::getInValidationRuleValues()` возвращает `Rule::in([])`, если для текущего состояния нет метки опции (`getOptionLabel` пуст), — сохранение падает с `validation.in`. Отсюда два практических следствия:

- **Опции должны включать текущее состояние, даже если оно «устарело».** Список услуг в составе записи собирается как «активные ∪ уже прикреплённые к записи» (`serviceOptions()`): услугу деактивируют, а не удаляют (история), и без этого старую запись нельзя сохранить. Прежний relation manager показывал все услуги через `relationship('service', 'name')` — проблемы не было.
- **Тесты с зашитыми датами становятся бомбой.** `BookingsRelationManagerTest` создавал слот с датой `2026-09-12`; форма создания предлагает только будущие слоты, и через три дня тест упал на `validation.in` по `slot_id`. Дата в тестах — `now()->addDay()`.

### Грабля: замыкание `whereHas` получает билдер, а не модель

`->modifyQueryUsing(fn (Builder $query) => $query->whereHas('slot', fn (Slot $slot) => $slot->date >= now()->startOfDay()))` — тип `Slot` в замыкании роняет страницу `TypeError` (Eloquent передаёт туда **билдер**), а без типа свойство `date` на билдере — undefined, и фильтр молча ничего не отсекает. Рабочая форма: `fn (Builder $slot) => $slot->where('date', '>=', now()->startOfDay())`. Тот же разбор — в `SlotsTable` (срез прошедших дней).

## Карточка услуги: прайс-правила и запрет удаления

Правка услуги (`/panel/booking/booking-services/{id}/edit`) показывает её прайс-правила таблицей ниже формы — `PriceRulesRelationManager` (связь `priceRules`, подключён через `BookingServiceResource::getRelations()`): «Добавить правило», «Изменить», «Удалить». Форма и таблица — те же, что в разделе «Прайс-правила», но с параметром: `PriceRuleForm::configure($schema, ?int $serviceId = null)` (при заданном id поля «Услуга» нет — услуга известна из владельца страницы) и `PriceRulesTable::configure($table, bool $withServiceColumn = true)`. Иначе формат «R-радиус» и перевод «рубли формы → копейки БД» жили бы в двух копиях.

**Проверка уникальности куба переехала с поля «Услуга» на поле «Радиус».** Услугу проверка берёт из параметра (карточка) либо из состояния формы (раздел). Форма, оставленная на неявном `service_id`, запрещала бы одинаковые правила у **разных** услуг — на это есть отдельный тест.

**Услуга с привязками не удаляется** (ADR 0025): Precondition `EnsureBookingServiceIsUnused` + `PanelAction::run` — тем же приёмом, что удаление бренда с товарами. Считаются все три привязки (прайс-правила, строки записей, комплексы — у всех FK `restrictOnDelete`), причём счётчики читает **сама проверка** (`loadCount`): забытый `withCount` у вызывающего молча выключил бы запрет, и удаление снова падало бы ошибкой БД. Один путь удаления на два места — `BookingServiceResource::deleteAction()` (табличное действие листинга и header-действие карточки). Вместо удаления услугу деактивируют: неактивная не видна клиенту, но остаётся в истории записей; удалить можно только услугу, которую нигде не использовали.

**Поиск по радиусу в таблице прайс-правил** — по цифрам строки: `R17`, `r17`, `17` → точное `radius = 17` (`PriceRulesTable::searchByRadius()`). `LIKE` не годится: радиусы 13…21, частичное совпадение даёт шум.

## Кнопка «Сохранить и закрыть» на страницах правки

Страницы правки записи, слота и услуги получают третью кнопку в ряду действий формы (`use SavesAndCloses;` — трейт `App\Filament\Concerns\SavesAndCloses`): сохранить и вернуться на экран, откуда оператор пришёл. Порядок: «Сохранить» → «Сохранить и закрыть» → «Отмена».

Адрес возврата — `$this->previousUrl` (Filament пишет его в `EditRecord::mount()` из `url()->previous()`, тот же источник, что у штатной «Отмены»), запасной — список раздела.

**Карточка слота возвращается только в список слотов** (`EditSlot::getReturnUrl()` сужает общий хук `SavesAndCloses::getReturnUrl()`): в неё попадают и из карточки записи, а возврат в запись замкнул бы круг «запись → слот → запись». Адрес экрана входа берётся, только если это сам список (адрес начинается с адреса листинга) — так переживают фильтры и страница листинга. У записи и услуги возврат прежний, экран входа: цикла у них нет, потому что карточка слота в запись больше не ведёт.

**Редирект делает сам `save()`** — трейт переопределяет `getRedirectUrl()` и включает его флагом перед сохранением, а не зовёт `redirect()` после `save()`. Так оператор остаётся на форме и при ошибках валидации, и при `DomainException` из Action со страничным `halt()` (например «на это время уже есть запись»): `save()` глотает `Halt` и выходит раньше редиректа, наружу сигнал не виден — свой редирект увёл бы со страницы вместе с сообщением об ошибке.

**Кнопка — не submit формы, а Livewire-метод** (`Action::make('saveAndClose')->action('saveAndClose')` → `wire:click`): у формы EditRecord один `wire:submit` (`save`), submit-кнопка отправила бы форму на него. Отложенное состояние полей уходит с тем же запросом — тест это проверяет.

Грабля: в тестах действие формы **не зовётся** через `callAction('saveAndClose')` — «action is not visible»: кнопка живёт в schema-компоненте `Actions` (футер формы), а хелпер ищет только смонтированные действия компонента. Рабочая форма — `->call('saveAndClose')` (то же, что посылает браузер) плюс `assertSee('Сохранить и закрыть')` на наличие кнопки; штатную «Сохранить» тесты зовут так же — `->call('save')`.

Вторая грань той же грабли (2026-09-18): у действия со **строковым** `->action('метод')` вызова через `callAction()` не происходит **вовсе** — `Action::getActionFunction()` возвращает `null` для строки (`vendor/filament/actions/src/Concerns/HasAction.php:27`), и `callMountedAction()` не зовёт ничего: ни ошибки, ни эффекта (запись просто не создаётся). В браузере кнопка работает — строковый `action` и есть прямой `wire:click` по методу компонента. В тесте — `->call('метод')`, а видимость проверяется отдельно (`assertActionVisible`/`assertActionHidden` + `assertSee`).

Хук `SavesAndCloses::getExtraFormActions()` — точка расширения ряда кнопок: страница правки возвращает свои действия (`EditBooking` — «Создать договор хранения»), порядок «Сохранить» → «Сохранить и закрыть» → «Отмена» → свои. У страницы создания аналог — переопределение `getFormActions()` (`CreateBooking` добавляет туда кнопку хранения).

## Раздел «Клиенты» и переходы из форм

**«Клиенты» (`UserResource`) — корневой раздел панели, вне кластеров** (`$navigationSort = 40` — после кластеров): клиент общий для каталога, заказов, записей и хранения. Листинг: ФИО (поиск по частям имени), телефон, почта, дата регистрации; форма: фамилия, имя (обязательно), отчество, телефон, почта. **Пароля нет** — входа клиента в панель нет, клиент опознаётся телефоном и SMS-кодом; **удаления нет** — на клиента ссылаются записи и договоры (FK `restrict`).

**Телефон хранится в каноне** «7XXXXXXXXXX» (`App\Support\Phone`): `dehydrateStateUsing(Phone::normalize)` при записи плюс **собственная проверка уникальности по канону**. Штатный `unique()` сверял бы сырой ввод: «8 912 345 67 89» и «79123456789» разошлись бы в проверке, а дубль упал бы уже ошибкой БД.

Кнопки-переходы между формами:

- **«Создать пользователя»** на создании договора хранения — `->url(UserResource::getUrl('create'))` + `->openUrlInNewTab()`: форма договора не теряется, а созданный клиент сразу находится поиском в поле «Клиент» (Select ищет на сервере).
- **«Создать договор хранения»** в форме записи (см. [Хранение колёс: домен Storage](storage-domain.md)) — появляется на услуге категории «Хранение»; на создании сохраняет запись и уводит на форму договора (`CreateBooking::getRedirectUrl()` по флагу), на правке — сразу уводит.

**Предзаполнение формы через адрес** — приём для переходов между формами: страница объявляет `#[Url]`-свойства (`CreateStorageContract`: `user_id`, `starts_on`, `price`; `CreateBooking`: `slot_id`), а в `fillForm()` дописывает их в состояние через `rawState()` — `fill()` дефолты полей теряет.

## Энумы в панели: контракт HasLabel

`->options(X::class)` для энума **без** `Filament\Support\Contracts\HasLabel` молча подставляет имя кейса, игнорируя собственный `label()` энума (`HasOptions::getOptions()`, `vendor/filament/forms/src/Components/Concerns/HasOptions.php:41`). Ни один энум проекта контракт не реализовывал — в панели жили `Winter`, `Alloy`, `Percent`, `Tire` вместо «Зимняя», «Литые», «Процент», «Шинные» (7 мест).

Фикс — `Season`, `WheelType`, `PromotionType`, `BrandType` получили `implements HasLabel` и трейт `App\Enums\Concerns\HasFilamentLabel` (адаптер `getLabel()` → доменный `label()`; трейт — потому что без него один и тот же метод копировался бы в каждый энум). Новый энум панели — `implements HasLabel` + `use HasFilamentLabel`; без контракта Filament откатится на имя кейса без единой ошибки.

## Заголовки страниц и ярлыки сущностей

Заголовок страницы Filament собирает из имени класса модели — до 2026-09-16 в 18 ресурсах из 19 жили `Brands`, «Создать Brand», «Редактирование Brand». Русский вид держится на трёх вещах:

- **`$modelLabel` / `$pluralModelLabel` на ресурсе.** Листинг берёт множественный ярлык (`getTitleCasePluralModelLabel()`), создание и правка — единственный (`CreateRecord::getTitle()`, `EditRecord::getTitle()` → `InteractsWithRecord::getRecordTitle()`). Те же ярлыки уходят в модалки действий и пустой список таблицы.
- **Подмена строк вендора** — `lang/vendor/filament-panels/ru/resources/pages/create-record.php` («Создание: :label») и `edit-record.php` («Изменение: :label»). Русский ярлык в именительном падеже не согласуется с глаголом («Создать Бренд», «Редактирование Бренд»); двоеточие снимает согласование сразу на всех ресурсах, вместо кастомного `getTitle()` на каждой странице. Laravel мержит подмену с файлом пакета через `array_replace_recursive` (`FileLoader::loadNamespaceOverrides`) — в файле подмены только изменённый ключ, остальные берутся из Filament.
- **`protected static bool $hasTitleCaseModelLabel = false;`** — Filament прогоняет ярлык через `Str::ucwords` (`HasLabels::getTitleCaseModelLabel()`), а тот капитализирует **каждое** слово: «Наценки На Доставку», «Склады Поставщиков». С флагом ярлык выводится ровно как объявлен, поэтому в коде хранится с большой буквы первого слова («Наценка на доставку»).

Грабля: `$hasTitleCaseModelLabel` объявлен в трейтe `HasLabels`, который подключает `Resource`, — переопределить свойство трейта в самом подключающем классе нельзя (фатальная ошибка), а в наследнике (`BrandResource extends Resource`) это обычное переопределение, одна строка на ресурс.

Стража — `tests/Feature/Admin/UiTitlesTest.php`: в ярлыках нет латиницы, в заголовке ровно одна заглавная буква (вернувшийся `ucwords` валит тест), строки «Создание: …» / «Изменение: …» закреплены — ключи вендора могут переехать при обновлении Filament, и подмена тогда тихо перестанет применяться.

Заголовок создания записи собирает `CreateBooking::getTitle()`: со страницы слота страница приходит с `?slot_id=` — «Создать запись в слот: 15.09.2026, 10:00»; кнопки «Создать» на листинге записей нет (`ListBookings` без header actions) — вход в создание один, со страницы слота. Заход по адресу без `?slot_id=` даёт заголовок «Новая запись» (до 2026-09-16 он ронял страницу: `Slot::findOrFail(null)`), а создание отвечает ошибкой «Слот не найден».

С того же `?slot_id=` берётся и слот для записи (`CreateAdminBooking`), и начало часа в поле «Время»; номер слота кладётся в состояние формы (`rawState`) — так варианты времени знают свой час, хотя поля «Слот» в форме нет.

Осталось английским по вине вендорских строк (не трогали): ярлык стоит **после** глагола в модалках действий и пустом списке — «Удалить :label», «Не найдено :model», «Все :label»; с русским ярлыком читается как «Удалить Бренд», «Не найдено Бренды». Лечится тем же приёмом — подменой ключа в `lang/vendor/filament-actions/ru/…`.

## Навигация (кластеры + группы)

Разделы группируются **кластером** — `app/Filament/Clusters/<Раздел>/`: кластер даёт один пункт верхнего уровня и поднавигацию внутри. Кластер «Каталог» (`CatalogCluster`) собрал 10 ресурсов и страницу импорта; внутри — группы поднавигации из `CatalogGroupEnum`: «Продукция» (Brands, TireProducts, WheelProducts, ProductModels), «Склады» (Warehouses, WarehouseMarkupRules, DeliverySchedules), «Точки выдачи» (CityPriceRules, DeliveryPoints), «Управление» (страница импорта `ImportProducts`). Панель — с верхним меню (`topNavigation()`).

**Принадлежность к кластеру задаётся явно свойством `$cluster` на каждом ресурсе/странице.** Filament не выводит её из расположения файла — каталог `Clusters/…` задаёт только размещение кода. Перенос файлов без `$cluster` даёт обратный эффект: кластер пуст и не виден (`canAccessClusteredComponents()` = false), а ресурсы остаются плоским списком. Кластеризация меняет URL разделов (префикс `/panel/catalog/...`) — ссылки строить только через `getUrl()`.

Экраны Cities и Countries из панели удалены (в кластер не переносились). ADR 0008 (обновлён).

Не всё обязано жить в кластере: **«Клиенты» (`UserResource`) — корневой ресурс** (`app/Filament/Resources/`, рядом с `NotificationResource`), `$navigationSort = 40` ставит его после кластеров. Клиент общий для каталога, заказов, записей и хранения — кластер для одного раздела не заводили (появится «Продажи» из волны 3 роадмапа — сгруппируем).

Кластер **«Шиномонтаж»** (`BookingCluster`, ADR 0012) — ресурсы записи на шиномонтаж; группы `BookingGroupEnum`: «Услуги» (BookingServices, PriceRules, ComplexServices), «Записи» (Slots, Bookings), «Хранение» (`StorageContracts` — договоры хранения колёс, домен Storage, ADR 0026: клиент, срок, стоимость, позиции повторителем со связью, закрытие кнопкой «Выдать колёса»), «Настройки» (ScheduleTemplates). Кнопка ручной генерации сетки живёт на расписании недели (`ListScheduleTemplates`), а не на листинге слотов: сетку держит планировщик, кнопка — ручной запуск того же `GenerateSlotGrid`.

**Хранение в панели — карточка и листинг** (2026-09-18): номер договора — первая колонка листинга и заголовок карточки; в листинге по нему **ищут** (колонки под номер нет — SQL по ID, приведённому к тексту с ведущими нулями). Кнопка «Распечатать договор» на карточке правки — header action, возвращающий `StreamedResponse`: файл формирует сервис домена, Livewire превращает ответ в скачивание (см. [Хранение колёс: домен Storage](storage-domain.md)).

Кластер **«Настройки»** (`SettingsCluster`, 2026-09-15) — настройки записи (`Settings`, переехали из «Шиномонтажа») и администраторы (`Admins`, переехали из плоского `app/Filament/Resources/`). Деньги в формах — рубли через `formatStateUsing`/`dehydrateStateUsing` (`numeric()` не совместим с Money-состоянием — NumberStateCast); record с Money-кастом гидратируется Livewire через `Wireable`. См. [Запись на шиномонтаж: домен Booking](booking-domain.md).
