## 4. Слои приложения (Layer Pattern)

```
HTTP → Middleware → Controller (thin) → FormRequest → Preconditions → Action::execute(DTO): DTO → Resource → HTTP
```

### 4.1. Маршруты (`routes/`)

| Файл | Префикс | Защита |
|------|---------|--------|
| `routes/api.php` | `/api` | Публичные + Sanctum |
| `routes/admin.php` | `/api/admin` | `auth:sanctum` (админская) |
| `routes/web.php` | — | Веб-страницы |
| `routes/console.php` | — | Artisan-команды |

### 4.2. Middleware

Промежуточная обработка: CORS, сессия, авторизация, rate limit.

### 4.3. Controller

Только оркестрирует. Не содержит бизнес-логики.
- CRUD → `{Entity}Controller` с методами
- Одно действие → `{Verb}{Entity}Controller::__invoke`

### 4.4. FormRequest

Валидация входящих данных. Только формат/структура, не бизнес-правила.

### 4.5. Preconditions

Бизнес-проверки. `ensure*()` → `DomainException`.
- Если проверок ≥3 — цепочка обязанностей через `setNext()`

### 4.6. Action (`final readonly class`)

Бизнес-логика.
- `execute(DTO): DTO`
- Не знает об HTTP
- Не вызывает другие Action (исключение: общая транзакция — через DI connection)
- Разделение чтения и записи

### 4.7. DTO (`final readonly class`)

Передача данных между слоями.
- `fromRequest()` / `toArray()`

### 4.8. Resource

Форматирование ответа API (Laravel API Resource).

## 5. Бизнес-модель

Компания — **малый продавец**, не производит и не закупает напрямую с заводов.

**Цепочка движения товара:**
```
Завод (поставщик) → Крупный продавец (наш склад) → Наша компания → Точка выдачи / Курьер → Клиент
```

**Сущности:**
| Сущность | Описание | Видит ли клиент |
|----------|----------|-----------------|
| **Поставщик (supplier)** | Завод-производитель (Cordiant, Nokian…). Внутренний справочник. Один бренд = один поставщик. | Нет |
| **Склад (warehouse)** | Крупный продавец/дистрибьютор, у которого мы покупаем товар. У каждого склада свои цены и остатки. Не равняется физическому адресу. | Нет |
| **Точка выдачи (delivery_point)** | Физическое место, где клиент забирает товар (самовывоз). Если в городе клиента нет точки выдачи — курьер. | Да |
| **Бренд (brand)** | Название модели товара (Winter Drive). Клиент видит бренд. Привязан к одному поставщику. | Да |

**Наличие товара в городе** = в городе есть хотя бы одна точка выдачи + товар есть на складе, с которым мы работаем.

## 8. Жизненный цикл заказа

```
              ┌────────────────┐
              │     Новый       │ ← создан клиентом
              │   (pending)     │
              └───────┬────────┘
                      │
              ┌───────▼────────┐
              │    Оплачен      │ ← платёжный шлюз (автомат)
              │    (paid)       │
              └───────┬────────┘
                      │
              ┌───────▼────────┐
              │  В обработке    │ ← менеджер подтвердил
              │  (processing)   │
              └───────┬────────┘
                      │
              ┌───────▼────────┐
              │  В доставке     │ ← менеджер передал ТК
              │  (shipped)      │
              └───────┬────────┘
                      │
              ┌───────▼────────┐
              │   Доставлен     │ ← менеджер отметил
              │  (delivered)    │
              └────────────────┘

Отмена (cancelled): клиент или менеджер из статусов Новый / Оплачен / В обработке
Возврат (refunded): менеджер из статусов В доставке / Доставлен
```

**Кто меняет статус:**
| Статус | Кто устанавливает | Действие |
|--------|------------------|----------|
| `pending` | Система | Клиент оформил заказ |
| `paid` | Система | Платёжный шлюз подтвердил оплату |
| `processing` | Менеджер | Подтвердил заказ |
| `shipped` | Менеджер | Передал ТК + трек-номер |
| `delivered` | Менеджер | Клиент получил |
| `cancelled` | Клиент / Менеджер | Отмена (с причиной) |
| `refunded` | Менеджер | Возврат средств |

## 9. Ценообразование

### 8.1. Формула цены для клиента

```
Финальная цена = (purchase_price × markup_coefficient) + city_markup
```

Где:
- **`purchase_price`** — закупочная цена (цена крупного продавца/склада)
- **`markup_coefficient`** — коэффициент наценки, зависит от склада и диапазона закупочной цены
- **`city_markup`** — фиксированная наценка (в рублях), зависит от города и диапазона нашей цены (`price`)

**Пример:**
```
Склад «ШиныОпт»: purchase_price = 4500
Правило наценки для склада: диапазон 0 — 5 000 → коэффициент 1.2
price = 4500 × 1.2 = 5400

Город Москва: цена 0 — 10 000 → наценка 240 ₽
Финальная цена = 5400 + 240 = 5640
```

### 8.2. Откуда берётся цена

| Поле | Откуда берётся | Описание |
|------|---------------|----------|
| `stocks.purchase_price` | Прайс от склада (импорт XLSX) | Цена, по которой мы купили у крупного продавца |
| `stocks.price` | Рассчитывается автоматически | `purchase_price × markup_coefficient` по правилу склада. Единая для всех городов базовая цена. |
| `catalog_prices.price` | Предрасcчитана и сохранена | Финальная цена для конкретного города (с city_markup, акциями и округлением). Используется для фильтрации, сортировки и отображения. |

При импорте прайса от склада: система загружает `purchase_price`, находит подходящее правило наценки для этого склада, вычисляет `price` и сохраняет оба значения. Если правило не найдено — `price = purchase_price` (наценка 1.0).

**`price` можно переопределить вручную** в админке (например, если нужно округлить или сделать спецпредложение).

### 8.3. Таблица `warehouse_markup_rules`

| Поле | Тип | Описание |
|------|-----|----------|
| `id` | PK | |
| `warehouse_id` | FK → warehouses | Склад |
| `price_from` | decimal(10,2) | Начало диапазона закупочной цены (включительно) |
| `price_to` | decimal(10,2) | Конец диапазона закупочной цены (включительно) |
| `coefficient` | decimal(5,2) | Множитель (например 1.2, 1.5, 2.0) |

**Правила поиска коэффициента:** по складу → среди правил находится первое, где `price_from ≤ purchase_price ≤ price_to`. Если правил несколько с пересекающимися диапазонами — применяется правило с наименьшим `price_from`, затем с наименьшим `price_to`.

### 8.4. Таблица `city_price_rules`

Наценка по городам — фиксированная сумма в рублях, зависит от `price` (нашей цены после наценки склада).

| Поле | Тип | Описание |
|------|-----|----------|
| `id` | PK | |
| `city_id` | FK → cities | Город |
| `price_from` | decimal(10,2) | Начало диапазона (включительно) |
| `price_to` | decimal(10,2) | Конец диапазона (включительно) |
| `markup` | decimal(10,2) | Фиксированная наценка в рублях (например 240) |

**Правила поиска:** по городу пользователя → среди правил находится первое, где `price_from ≤ stocks.price ≤ price_to`. Если правил несколько — применяется правило с наименьшим `price_from`, затем с наименьшим `price_to`.

### 8.5. Таблица `catalog_prices` — предрасcчитанные финальные цены

Чтобы при фильтрации и сортировке по цене в каталоге не пересчитывать каждый раз цену для всех товаров, финальная цена предрасcчитывается и хранится отдельно.

| Поле | Тип | Описание |
|------|-----|----------|
| `id` | PK | |
| `stock_id` | FK → stocks | Остаток (привязка к товару и складу) |
| `city_id` | FK → cities | Город |
| `price` | decimal(10,2) | Финальная цена: `round(price + city_markup − discount, -2)` |
| `delivery_min` | smallint | Минимальный срок доставки (рабочих дней) |
| `delivery_max` | smallint | Максимальный срок доставки (рабочих дней) |

**Формула срока доставки для строки `catalog_prices`:**

```
stock → warehouse → delivery_schedules (несколько записей, по дням недели)
city → city_delivery_times.delivery_days

min_before = MIN(days_before)   — лучший days_before среди всех дней отгрузки склада
max_after  = MAX(days_after)    — худший days_after среди всех дней отгрузки склада
max_idle   = MAX(кол-во дней между соседними днями отгрузки) — самый долгий перерыв

delivery_min = min_before + city_delivery_days
delivery_max = max_after + max_idle + city_delivery_days
```

Если для склада не задан график отгрузки — используется значение по умолчанию (из конфига).

**Пример со складом: ПН(3/5), ВТ(4/5), нет СР-ЧТ, ПТ(2/4):**

```
min_before = 2 (с ПТ)
max_after  = 5 (с ПН, ВТ)
max_idle   = 3 (ВТ→ПТ = 3 дня без отгрузок)

Город с city_delivery_days = 2:
  delivery_min = 2 + 2 = 4 дня
  delivery_max = 5 + 3 + 2 = 10 дней
```

**UNIQUE:** `(stock_id, city_id)` — один остаток × один город = одна строка.

**Когда пересчитывается `catalog_prices`:**

| Событие | Действие |
|---------|----------|
| Изменился `stocks.price` (цена от склада) | Пересчитать строки для этого stock_id по всем городам |
| Изменились `city_price_rules` (наценка города) | Пересчитать строки для всех stock_id, попадающих под диапазон изменения |
| Изменилась активная акция (создана/удалена/изменена) | Пересчитать строки для затронутых товаров по всем городам |
| Изменился `delivery_schedules` (график склада) | Пересчитать строки для всех stock_id этого склада по всем городам |
| Изменились `city_delivery_times` (срок до города) | Пересчитать строки для этого city_id по всем stock_id |
| Импорт нового прайса от склада | При создании новых stocks — сразу рассчитать catalog_prices |

**Сценарии работы:**
- **Каталог (список с фильтрацией):** `SELECT ... FROM catalog_prices WHERE city_id = ? AND price BETWEEN ? AND ?` — один индекс, без расчётов на лету
- **Карточка товара:** один lookup по `catalog_prices` для города пользователя
- **Пересчёт:** запускается через очередь (Job) после любого изменения цен/правил/акций

### 8.6. Акции

Акция определяется только датами: если `now` между `starts_at` и `ends_at` — акция активна. Статусов нет.

Поверх финальной цены может применяться скидка по акции. Цена со скидкой включается в `catalog_prices.price` при пересчёте.

```
Цена со скидкой = round(базовая_цена_города − discount, -2)
              или = round(базовая_цена_города × (100 − discount%) / 100, -2)
```

**Типы привязки акции (`promotable_type`):**

| `promotable_type` | `promotable_id` | Пример |
|-------------------|----------------|--------|
| `tire_product` или `wheel_product` | ID товара | Скидка на конкретную шину |
| `brand` | ID бренда | Скидка на все товары бренда |
| `all` | null | Скидка на весь каталог |

**Правило выбора акции:** если на товар попадает несколько активных акций, применяется та, что привязана к более конкретному объекту:
1. акция на **конкретный товар** → выше чем на бренд
2. акция на **бренд** → выше чем на весь каталог (`all`)
3. внутри одной категории — с большей скидкой

### 8.7. Полный путь формирования цены

```
purchase_price (из прайса склада)
       │
       ▼
применяем markup_coefficient (из warehouse_markup_rules)
       │
       ▼
stocks.price = purchase_price × coefficient
  (единая базовая цена товара, хранится в БД)
       │
       ▼
определяем город пользователя
       │
       ▼
применяем city_markup (из city_price_rules по городу и stocks.price)
       │
       ▼
catalog_price = stocks.price + city_markup
  (финальная цена для данного города, рассчитывается на лету)
       │
       ▼
если есть активная акция → применяем скидку
       │
       ▼
округление до 100 ₽ в меньшую сторону
       │
       ▼
Цена в каталоге / корзине = финальная цена для клиента
```

**Правило округления:** финальная цена округляется математически до ближайших 100 ₽.

**Примеры:**
```
5640 → 5600
5650 → 5700
5499 → 5500
5449 → 5400
5500 → 5500
999  → 1000
949  → 900
```

## 10. Сроки доставки

### 10.1. Бизнес-логика

Мы (наша компания) находимся в **Челябинске**. Товар движется по цепочке:

```
Склад (крупный продавец)
       │  days_before / days_after — время до нас
       ▼
Мы в Челябинске
       │  city_delivery_days — время из Челябинска до города клиента
       ▼
Точка выдачи / Курьер → Клиент
```

У каждого склада может быть **несколько дней отгрузки** с разными параметрами. Например:

```
ПН до 15:00 → 3 дня, после → 5 дней
ВТ до 16:00 → 4 дня, после → 5 дней
ПТ до 10:00 → 2 дня, после → 4 дня
СР, ЧТ       → отгрузок нет
```

### 10.2. Расчёт `delivery_min` и `delivery_max` в `catalog_prices`

Для каждой строки `(stock_id, city_id)`:

**`delivery_min`** — минимальный срок (лучший случай):
```
delivery_min = MIN(days_before) + city_delivery_days
```
Берём наименьший `days_before` среди всех дней отгрузки склада.

**`delivery_max`** — максимальный срок (худший случай, с учётом ожидания следующей отгрузки):
```
delivery_max = MAX(days_after) + city_delivery_days + max_idle_days
```
Где `max_idle_days` — самый длинный промежуток между днями отгрузки (сколько дней придётся ждать, если не успели к отсечке).

**Пример расчёта для склада с графиком выше:**

```
Дни отгрузки: ПН, ВТ, ПТ
Промежутки: ПН→ВТ = 1 день, ВТ→ПТ = 3 дня, ПТ→ПН = 3 дня
max_idle_days = 3

MIN(days_before) = 2 (ПТ)
MAX(days_after)  = 5 (ПН, ВТ)

Каталог для города с city_delivery_days = 2:
  delivery_min = 2 + 2 = 4 дня
  delivery_max = 5 + 3 + 2 = 10 дней
```

### 10.3. Реальный срок на момент просмотра (отображение)

В карточке товара и в корзине клиент видит **конкретный срок**, рассчитанный на текущий момент.

**Логика расчёта на лету:**

```
ТЕКУЩИЙ день недели + время
       │
       ▼
Есть ли у склада отгрузка СЕГОДНЯ?
       │
       ├── ДА: сейчас ≤ cutoff_time?
       │        ├── ДА → срок = days_before + city_delivery_days
       │        └── НЕТ → следующий день отгрузки + days_after + city_delivery_days
       │
       └── НЕТ → ближайший день отгрузки + days_after + city_delivery_days
```

**Примеры для склада (ПН до 15:00 дней, ПТ до 10:00) и города с доставкой 2 дня:**

```
Посещение в ПН в 14:00 → ПН до 15:00 → 3 + 2 = 5 рабочих дней
Посещение в ПН в 16:00 → после отсечки, след отгрузка ПТ → days_after=4 + 2 = 6 дней (+ожидание ПН→ПТ)
Посещение в СР → нет отгрузки, след ПТ → days_after=4 + 2 = 6 дней (+ожидание СР→ПТ)
```

**Где применяется:**
- **Карточка товара** — конкретный срок для выбранного города с учётом дня/времени посещения
- **Корзина** — пересчёт при оформлении (на момент создания заказа)
- **Каталог (фильтр)** — используется `delivery_min` / `delivery_max` из `catalog_prices`

### 10.4. Что видит клиент

| Где | Что показывает |
|-----|---------------|
| **Карточка товара** | Конкретный срок на текущий момент: «Доставка в Екатеринбург — 5 рабочих дней» |
| **Корзина** | Срок для блока «Информация о доставке» — пересчитывается при входе в корзину |
| **Фильтр каталога** | Предустановленные варианты: «доставка до 3 дней», «доставка 3–7 дней», «доставка от 7 дней» |

**В карточке товара срок зависит от текущего момента:**
- Зашёл в ПН в 14:00 → срок 5 дней (успевает к отсечке)
- Зашёл в ПН в 16:00 → срок 6 дней (не успел, следующая отгрузка)
- Зашёл во ВТ в 14:00 → срок 6 дней

### 10.5. Фильтрация по сроку доставки в каталоге

Для фильтра используется предрасcчитанный диапазон из `catalog_prices`:

```
товары с доставкой до 3 дней    → WHERE delivery_min <= 3
товары с доставкой 3–7 дней     → WHERE delivery_min BETWEEN 3 AND 7  
товары с доставкой от 7 дней    → WHERE delivery_min >= 7
```

Фильтр оперирует `delivery_min` (лучший случай), чтобы не отсекать товары, которые при своевременном заказе придут быстро.

### 10.6. Таблица `delivery_schedules`

| Поле | Тип | Описание |
|------|-----|----------|
| `id` | PK | |
| `warehouse_id` | FK → warehouses | Склад |
| `day_of_week` | smallint | День отгрузки (0=пн ... 6=вс) |
| `cutoff_time` | time | Время отсечки (до которого часа принимаем заказ в этот день) |
| `days_before` | smallint | Рабочих дней до нас, если успели до отсечки |
| `days_after` | smallint | Рабочих дней до нас, если не успели |

UNIQUE: `(warehouse_id, day_of_week)`. Если для склада нет записи на день недели — отгрузки в этот день нет.

### 10.7. Таблица `city_delivery_times`

| Поле | Тип | Описание |
|------|-----|----------|
| `id` | PK | |
| `city_id` | FK → cities | Город клиента |
| `delivery_days` | smallint | Рабочих дней из Челябинска до города |
| `priority` | smallint | Порядок показа в фильтре доставки (опционально) |

### 10.8. Пересчёт `catalog_prices` при изменении расписания

| Событие | Действие |
|---------|----------|
| Изменился `delivery_schedules` (график склада) | Пересчитать `delivery_min/delivery_max` для всех stock_id этого склада по всем городам |
| Изменились `city_delivery_times` | Пересчитать `delivery_min/delivery_max` для этого city_id по всем stock_id |

## 13. Ключевые архитектурные решения (ADR)

| Решение | Обоснование |
|---------|-------------|
| Монолит, а не микросервисы | Проект e-commerce, нет смысла дробить |
| PostgreSQL, а не MySQL | Надёжнее для сложных выборок каталога |
| Фасеты в ответе каталога, а не отдельным запросом | Один запрос = полная страница, без лишних round-trip |
| Полиморфные stocks/images/promotions | Единый механизм для шин и дисков |
| Раздельные tire_products / wheel_products | Разные атрибуты — не влезают в одну таблицу |
| Гостевая корзина по device_id | Не требует регистрации, повышает конверсию |
| Нет промокодов, бонусов, отзывов | Сознательное упрощение первой версии |
