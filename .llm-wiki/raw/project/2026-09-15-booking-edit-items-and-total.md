# Правка записи в панели: состав в форме, цена по прайсу, итог (ФТ-19)

> Source: Проект, сессия 2026-09-15 (плана `.claude/plans/booking-edit-items-and-total.md`, прогоны и отклонения там же)
> Collected: 2026-09-15
> Published: 2026-09-15

## Запрос

Правки страницы `/panel/booking/bookings/{id}/edit`:

1. заголовок — «Запись ФИО, телефон»;
2. при смене радиуса меняется стоимость уже прикреплённых услуг, у которых цена зависит от радиуса;
3. в схеме — итоговая стоимость как сумма всех прикреплённых услуг с их количеством;
4. итоговая стоимость записи пересчитывается при сохранении;
5. при создании новой услуги в записи услуга подтягивается с готовой ценой по правилам из таблицы прайса.

## Развилка: relation manager или повторитель в форме

`ItemsRelationManager` (таблица состава под формой) — отдельный Livewire-компонент: он читает **сохранённую**
запись из БД и не видит радиус, выбранный в форме, но ещё не сохранённый. Живой пересчёт цены при смене радиуса
в нём невозможен — только пересчёт после сохранения, который вдобавок молча затирал бы цену, поправленную
оператором в модалке. Решение пользователя (по рекомендации): состав переезжает в **повторитель внутри формы
записи**, relation manager со страницы убран (файл удалён, регистрация `getRelations()` снята).

Выбранный вариант закрыл сразу четыре требования: радиус и строки живут в одном компоненте, цена пересчитывается
на глазах, итог виден в схеме, сохранение идёт одним путём.

## Реализация

| Место | Что |
|---|---|
| `EditBooking::getTitle()` | «Запись {имя}, {телефон}» из `booking.user`, пустые части опускаются |
| `EditBooking::mutateFormDataBeforeFill()` | строки состава отдаются в форму снимком цены (`price` в рублях строкой), а не пересчётом по текущему прайсу |
| `BookingForm` | повторитель `items` в табличном виде (`->table()` + `TableColumn`): услуга / цена / количество; `visibleOn('edit')`, `minItems(1)` |
| `BookingForm::serviceSelect()` / `quantityOptions()` | общие для составов create и edit (повтор и опции 1–4 из констант `PriceCalculator`) |
| `BookingForm::fillItemPrice()` | выбор услуги → цена за единицу по кубу (услуга × радиус × тип записи); нет комбинации — уведомление `DomainException`, цена не меняется |
| `BookingForm::repriceItems()` | `radius`/`car_type` с `->live()`: цена следует за прайсом у услуг **с правилами**, у услуг без правил снимок не трогается |
| `Placeholder::make('items_total')` | «Итоговая стоимость» = Σ(цена × количество), пересчитывается на рендере |
| `UpdateAdminBooking` (+`UpdateAdminBookingInput`, `BookingItemInput`) | транзакция: снимок полей, синхронизация строк по `service_id` (`updateOrCreate` + удаление отсутствующих), `total_price` из сохранённых строк |
| `EditBooking::handleRecordUpdate()` | собирает DTO и вызывает Action (не `$record->update($data)`) |

Правила, зафиксированные в тестах: цена из формы сохраняется как есть (ручная правка оператора — ФТ-19, Action
прайсом не переписывает); итог считается из строк «цена за единицу × количество»; повторное сохранение не
пересоздаёт строки (id сохраняются).

## Грабля: Filament валидирует значение Select по его опциям

`Select` с `->options()` в Filament 5 добавляет правило `in` (`Select::getInValidationRuleValues()`: пустая метка
опции для текущего состояния → `Rule::in([])`) — сохранение падает с `validation.in`. Два следствия:

- тест прошлой сессии создавал слот с датой `2026-09-12`; когда дата стала прошедшей, форма создания перестала
  предлагать этот слот и тест упал — тест-«дата-бомба»;
- список услуг в составе записи должен включать **деактивированные** услуги, уже прикреплённые к записи
  (`serviceOptions()`: активные ∪ `service_id` строк записи), иначе старую запись нельзя сохранить. У прежнего
  relation manager'а проблемы не было — его `relationship('service', 'name')` показывал все услуги.
